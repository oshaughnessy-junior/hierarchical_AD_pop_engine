> **Superseded (2026-05-18).** This plan was written when the implicit
> prototype was un-validated. The prototype is now validated end-to-end
> (engine v2 ↔ Backup 2 JS = 0.003; engine v2 ↔ Backup 1 particle MC at
> self-consistent depletion fraction JS ≈ 0.007), the cell-area
> Jacobian fix has landed in both engine paths, and ε has absolute
> physical meaning. The canonical production-migration plan is now
> [PLAN_engine_v2_production.md](./PLAN_engine_v2_production.md). This
> file is kept for historical context.

## Motivation

Red-team Phase 1 validation (`PLAN_red_team_validation.md`) established
empirically that the current engine's perturbative accumulator
(`CoagulationResponse._solve`) matches the gold-standard implicit
solver only at unphysically small effective coupling ε ≈ 0.025. The
physical regime — where 2G / 3G peaks are visible in real GW catalogues
— is at ε ~ O(1), far outside the perturbative truncation's domain of
validity.

The proposed solver: damped Picard fixed-point on the steady-state
coagulation equation

    N(m, χ) = N_natal(m, χ) + gain[N, N](m, χ) − loss[N](m, χ)

where the bilinear gain re-uses the engine's existing
``_step_one_generation`` (with sym = 1/2) and the loss is a new term
the perturbative accumulator omits entirely.

A working 2D prototype is in `red_team/engine_v2_implicit.py` and is
plotted as the fifth curve in `red_team/compare_all.py`. This plan
covers what's needed to make it production.

## Step 1 — validate the prototype

Run `python -m red_team.compare_all --epsilon 1.0` and check, on a
**moderate-coupling** Stage 1 θ\*:

- `engine_v2 ↔ backup1` JS < 0.05 on `dN/dm` and `dN/dχ`.
- `engine_v2 ↔ backup2` JS < 0.05 on `dN/dm` (mass-only).
- `engine ↔ engine_v2` JS *substantially* worse than the above —
  confirms the current engine's perturbative truncation is the
  bottleneck.

If the prototype fails either of the first two, debug:

- Picard convergence: bump `max_iter`, lower `damping` (we use 0.4 by
  default), look at the convergence trace to spot oscillation.
- Loss-term normalisation: cross-check the 4D einsum trapezoid weights
  against a 1D analytic integral on a uniform population.

If both pass, proceed.

## Step 3 — AD support via implicit-function-theorem custom VJP

The Picard loop is not natively AD-friendly: JAX would unroll the loop
and differentiate through every iteration. That's both slow (O(iter ×
N²) memory) and brittle (a non-converged loop produces noisy gradients).

The standard fix is a custom VJP at the fixed point: given converged
`N` satisfying `N = F(N, θ)` with `F = N_natal(θ) + C(N, θ)`, the
gradient is

    dN/dθ = (I − ∂F/∂N)⁻¹ · ∂F/∂θ

evaluated at the converged `N`. JAX has `jax.lax.custom_root` and the
implicit-function-theorem hooks needed.

Effort: ~1 session. Reference: `jaxopt.implicit_diff.custom_root`
(or hand-rolled). Test via finite-difference vs. AD on a small θ
perturbation; agreement within ~1 e-4 relative confirms.

## Step 4 — switch Stage 1 demo to `solver="implicit"`

Once Step 3 lands, edit `demo/demo_gwkokab_fit_stage1.py` to build the
response with `solver="implicit"`. Re-run the SVI/NUTS fit; recovery
should now be on the *physically meaningful* cascade, not the
small-ε truncation. Expect the 6-parameter recovery to land cleanly
inside the 90% credible intervals — and, more importantly, the
*shape* of the recovered `dN/dm` should now show real 2G/3G structure
when θ\* warrants it.

If recovery on the existing mock catalog gets *worse* (wider posteriors,
shifted means), that's a feature not a bug: the mock catalog was
generated by the buggy engine and the implicit engine sees through it.
The clean test is to regenerate the mock catalog with `solver="implicit"`
and re-fit.

## Step 5 — performance pass

Picard iteration on a (96, 32) grid: ~75 MB / iter, ~100 iters ⇒
~8 GB of total array ops per solve. For NUTS, this is once per
leapfrog step; for typical 500 warmup × 1000 samples = 1500 solves
≈ 12 TB of array ops total. Tractable on GPU; CPU-laptop runtime
≈ tens of minutes to hours.

Options if too slow:

- Lower-resolution fit grid (`N_m=48, N_chi=16`) — quartic speedup.
- Cache the converged `N` and warm-start subsequent Picard iterations
  from neighbouring θ samples (most warmup transitions are small θ
  moves).
- Anderson acceleration instead of damped Picard — typically 3–5×
  fewer iterations.

Defer until Step 4 reveals a real wallclock problem.

## Open questions

1. **Convergence at edge θ**: damped Picard converges for the Stage 1
   centre. Does it for the corners of the prior box (extreme spin loc
   / scale, large kernel_b)? Add a regression test sweeping ten random
   points from the prior.
2. **Loss-term retention coupling**: the loss term includes
   `P_retain(m, m', χ, χ')` — a 4D Heaviside. Its gradient w.r.t.
   `v_esc` is zero almost everywhere, same constraint as the existing
   engine. Document explicitly so the AD path is well-defined.
3. **Negative `N_new` excursions**: we clip the Picard update to
   `N_new ≥ 0`. This is a non-smooth clip and can hurt convergence at
   high coupling. If observed, replace with a softplus-style clip with
   tunable temperature.

## Anti-goals

- Don't delete `_solve` in this refactor — keep it as a perturbative
  reference / diagnostic. Removal is a separate cleanup once the
  implicit solver has shipped for ≥ 1 minor version.
- Don't try to make the implicit solver work with `k_max` < ∞. Picard
  iteration to convergence *is* the all-orders sum. The `k_max`
  parameter becomes a no-op for `solver="implicit"`.
- Don't try to introduce a separate "time" knob like Backup 2's ε.
  The implicit solver converges to the steady state directly;
  exposing a half-evolved time-slice would re-introduce the
  small-ε pathology we are escaping.
